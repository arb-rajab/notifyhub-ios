# Ops

## Build system: XcodeGen, not a committed .xcodeproj

`project.yml` is the source of truth; `NotifyHubIOS.xcodeproj` is
generated by `xcodegen generate` and is `.gitignore`d - never commit it,
and never hand-edit it (regenerate from `project.yml` instead). This
avoids the merge-conflict-prone, hard-to-hand-author `.pbxproj` format
entirely, which matters especially in this repo's case: this development
sandbox has **no Xcode installed and no Swift toolchain at all** (a
Linux container), so a hand-authored `.pbxproj` could not have been
validated by anyone or anything before CI's first run.

## Building locally (on an actual Mac with Xcode)

```bash
brew install xcodegen
xcodegen generate
open NotifyHubIOS.xcodeproj
```

Or from the command line:

```bash
xcodebuild build -project NotifyHubIOS.xcodeproj -scheme NotifyHubIOS \
  -destination 'platform=iOS Simulator,name=iPhone 15'
xcodebuild test -project NotifyHubIOS.xcodeproj -scheme NotifyHubIOS \
  -destination 'platform=iOS Simulator,name=iPhone 15'
```

No `CODE_SIGNING_ALLOWED=NO` needed (or wanted) here - `project.yml` sets
ad-hoc signing (`CODE_SIGN_IDENTITY: "-"`) for both targets, which needs
no paid Apple Developer account or provisioning profile for a Simulator
destination. A fully unsigned build launches in the Simulator fine, but
Keychain Services entitlement checks fail with `errSecMissingEntitlement`
without at least ad-hoc signing - `KeychainStoreTests` is what caught
this in CI.

(Substitute whatever Simulator is actually installed - CI discovers one
dynamically rather than hardcoding a name for exactly this reason; see
`.github/workflows/ci.yml`.)

## CI

`.github/workflows/ci.yml` runs on `macos-14`: installs XcodeGen,
generates the project, picks an available iPhone Simulator via
`xcrun simctl list devices available`, then builds and tests with code
signing disabled (`CODE_SIGNING_ALLOWED=NO`) - no provisioning profile
or signing identity is needed to build/test against a Simulator.

## Real device / real push testing

Requires, entirely outside any automated session:

1. A real Apple Developer Program account and a real provisioning
   profile / signing identity for `com.notifyhub.ios` (or a
   re-bundle-identified fork).
2. `NotifyHubIOS.entitlements`'s `aps-environment` set to
   `development` (Simulator/dev builds - already the default in
   `project.yml`) or `production` (TestFlight/App Store), matching
   whichever APNs environment the notifyhub backend is configured to
   send to.
3. notifyhub's own APNs credentials (`APNS_KEY_ID`, `APNS_TEAM_ID`,
   `APNS_BUNDLE_ID`, `APNS_PRIVATE_KEY`) set in an operator's own local
   environment - never in notifyhub's repo or CI (notifyhub's ADR-008).
4. A physical iOS device (APNs registration does not work in the
   Simulator at all before Xcode 14's Simulator push support, and even
   with that support, real Apple-delivered pushes still require a
   physical device - the Simulator's push support is for
   locally-injected test payloads via `xcrun simctl push`, not real
   end-to-end delivery from Apple's servers).

This entire path is permanently outside what any session working in
this sandbox can do or verify - see [08-risk.md](./08-risk.md) R-1.

## Host configuration

`Endpoints.swift` reads `NotifyHubHost` from `Info.plist` (falling back
to `localhost:4000`, matching notifyhub's `npm run dev` default). Point
this at a real deployed notifyhub host via an Xcode build setting /
`project.yml` `info.properties` override per environment - never commit
a real production host here as a "default."
