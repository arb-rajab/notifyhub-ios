# Risk Register

| ID | Risk | Likelihood | Impact | Mitigation / status |
| --- | --- | --- | --- | --- |
| R-1 | Real APNs device-push delivery can never be verified end-to-end from this sandbox or from CI - it needs a real Apple Developer `.p8` key, Team ID, a physical iOS device, and notifyhub's own live credentials, none of which can exist here by design (ADR-006, mirrors notifyhub's ADR-008/R-8). | Certain - a standing constraint, not a probability | Low for this app's own routing/parsing logic (covered by `DeepLinkCoordinatorTests` against the real payload contract); the residual risk is entirely in the untested Apple-side delivery path | **Permanent, by design.** Anyone needing live-delivery assurance runs the app on a physical device with real credentials outside any automated session. |
| R-2 | Nothing in `Sources/` or `Tests/` has ever been compiled in this development sandbox (no Xcode/Swift toolchain - a Linux container). All Swift syntax, API availability (iOS 16 deployment target), and type-checking correctness is unverified until CI's first run. | Medium until first CI run, then resolved | Medium (a compile error would block CI, not silently ship) | `.github/workflows/ci.yml`'s `build-and-test` job is the first real verification. Written conservatively (iOS-16-compatible API forms used throughout, e.g. the single-parameter `onChange` overload, not the iOS-17 two-parameter one) specifically to reduce first-CI-run failures, but that carefulness is not a substitute for the job actually passing. |
| R-3 | `GraphQLSubscriptionClient` has no reconnect/retry logic - if the WebSocket connection drops (backgrounding, network change), live updates on an open `ChannelDetailView` silently stop until the view is re-opened. | Medium in real-world use (mobile networks drop connections routinely) | Medium (degrades to "pull to refresh works, live updates don't" rather than a crash) | Not implemented this session - tracked in [09-backlog.md](./09-backlog.md). The initial `notifications` query load means the user never sees stale-forever data, only stale-until-next-visit live data. |
| R-4 | No refresh-token flow - this app inherits notifyhub's own accepted tradeoff (ADR-003 on notifyhub's side: no server-side session, no refresh token, 15-minute JWTs). A session that goes idle for 15+ minutes then tries an authenticated action gets an `UNAUTHENTICATED` GraphQL error with no automatic recovery beyond re-login. | Medium (15 minutes idle is not unusual for a mobile app backgrounded and returned to) | Medium (forces a re-login, not a crash or data loss) | Matches notifyhub's own accepted tradeoff; would need to change on both sides together if addressed. Tracked in [09-backlog.md](./09-backlog.md). |
| R-5 | `PushRegistrationService.rotate`'s fallback-to-`register` path (when `oldToken` is unknown) and the "retry registration after sign-in" path in `AppSession.registerCurrentAPNsTokenIfNeeded()` are both best-effort and swallow errors silently (`try?`) - a failed registration has no user-visible signal or retry-later mechanism beyond the next app launch/foreground. | Low (registration failures should be rare - the main legitimate failure mode, not being signed in yet, self-heals on next sign-in) | Low (degrades to "this device doesn't receive push until the next successful registration," not a hard failure of any other feature) | Accepted for this session's scope; tracked in [09-backlog.md](./09-backlog.md) if telemetry/retry becomes a real requirement. |
| R-6 | No SwiftUI view-level (snapshot/UI) tests - only `ViewModel`s and the networking/auth/push layers have automated tests. A view-only regression (e.g. a broken binding that compiles fine) would not be caught by this test suite. | Low-Medium | Low-Medium (would surface immediately in manual/CI-build smoke testing, just not in an automated assertion) | Accepted, documented tradeoff for this session's scope - see [05-testing.md](./05-testing.md). |
